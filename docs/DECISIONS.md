# 关键设计决策

> 2026-09-28（T33）：项目改为只做联邦 Agent。D1–D22、D25、D26 随原来的 7 个维度、4 个场景、组队流程和沙箱架构一起废弃，保留在下文作为记录。D23 中"界面与命令行共用一套 API"、D24 中"Agent 用我方 OpenAI 兼容的大模型接口"这两条仍然有效，已并入 D27、D31。当前有效的决策从 D27 起，后续新增见文末。

## D1：以工作负载为第一选择

状态：由 D8–D10 细化（2026-09-24）。入口仍是"想完成什么"，但改为"协作目标"维度，工作负载变为维度 1–5 落到的场景模板。

用户通常先知道“想完成什么”，而不是先知道 FedAvg、MPC 或某个框架名。因此入口是工作负载，算法和运行时在下一层出现。

## D2：数据关系与参与拓扑分开

状态：采用

横向/纵向描述数据分布，Cross-silo/Cross-device 描述组织和设备形态。两者影响不同的算法、协议、资源和治理要求，不能合并成“数据类型”。

## D3：用保护目标替代单一“加密方式”

状态：采用

SecAgg、DP、HE、MPC 和 TEE 解决的问题不同，也可能组合使用。用户先选隐藏单方更新、样本级隐私、加密计算等目标，平台再映射机制，并在后端验证 runner 是否真的支持。

## D4：运行时和输出由平台解析

状态：采用

Flower、FATE 或自定义 worker 不应成为与业务目标平级的自由选项。平台根据工作负载、策略、拓扑和保护要求选择兼容 runner；评测和输出同理。

## D5：统一控制面，不统一算法语义

状态：采用

所有任务共享 Run 生命周期和基础设施契约，但模型训练、PSI、联邦统计、FedRAG 和 Skill merge 使用不同 runner adapter。通用性体现在可插拔契约，而不是一个巨大执行器。

## D6：硬规则优先于 Agent

状态：采用

格式、schema、模型架构、隐私预算和权限等确定性条件由 policy engine 决定。Agent 负责解释、建议和长尾分析，不能绕过拒绝结果，也不能直接执行上传内容。

## D7：先打通一条纵向切片

状态：调整（2026-09-24）。先用前端确认维度分层，再选两个结构差异大的场景做后端 demo；LoRA 仍是候选之一。

前端可以展示完整平台边界，但后端第一阶段只实现 PEFT / LoRA。完成上传、准入、沙箱、执行、评测和发布后，再接第二类工作负载验证抽象。


## D8：维度按"用户最先能回答的问题"排序，只有前层约束后层

状态：采用（T14，2026-09-24）

顺序为协作目标 → 各方投入 → 数据关系 → 参与方形态 → 模型形态 → 协作策略 → 安全与信任 → 场景参数。算法和保护依赖前面所有信息，所以放在最后。单向约束保证后面的选择不会让前面失效。

## D9：新增"各方投入"维度

状态：采用（T14）

"多轮联邦训练"和"已训练产物聚合"的差别在于各方拿出来的是什么，而不是两个平台。用这个维度统一两者，并由它决定输入接入方式和执行模式。

## D10：新增"模型形态"维度，场景模板变为路径落点

状态：采用（T14）

模型类别放在策略之前约束策略，解决"树模型 + FedAvg"这类非法组合；LoRA 等成为同一层下的共享方式（个性化、异构已在 D13 中删除）。9 类工作负载改为 10 个场景模板（PEFT 拆成联邦微调与已训练产物聚合），作为维度 1–5 的落点，同时保留模板快捷入口。

## D11：保护可用性由计算类型和 runner 能力判断

状态：采用（T14）

每条策略声明计算类型（可加、比较、拼接组合、纵向协议、需理解内容），保护预设据此判断能否使用，并给出原因。不用"某场景不能用某保护"的黑名单。完整性（鲁棒聚合）曾作为可选叠加，已在 D13 中删除。

## D12：前端统一 FrontendRunPlan，按执行模式模拟

状态：采用（T15）

删除旧 LoRA mock，所有场景共用一个状态机，由模拟器按执行模式生成阶段内容，并显示真实耗时预估。FrontendRunPlan 是后端 RunSpec 的前身。

## D2 补充：本地模拟不属于参与方形态

2026-09-24：本地模拟是运行环境，移到执行预设；"无训练数据协作"不再是数据关系取值，改为数据关系不适用时隐藏该维度。

## D13：只收录主流方法，大模型 / Agent 相关方法保留并标"前沿"

状态：采用（T17，2026-09-24）

平台的分层用来帮用户选到实际可用的方法，而不是做学术综述。只保留有成熟开源实现、实际用得多的方法；小众方法即使在论文和 benchmark 里很成熟也不收录；大模型 / Agent 相关的方法还在快速演进，但方向重要，保留并标"前沿"。"成熟 / 试点 / 研究"三档标签取消，主流方法不打标签。删除清单见 DIMENSIONS.md 的"未收录"。

## D14：场景作为维度 1，定位场景的问题作为它的子项

状态：采用（T20，2026-09-24）

原来的维度 1–5 实际上都是在定位场景，场景是它们的落点。把场景提升为维度 1、原维度 1–5 改为子项 1.1–1.6，能直接表达"先确定场景，再在场景内选方法"。已选选项再点一次即取消；场景确定后子项必须保留一个选择，不能取消，想换场景就直接点另一个场景或取消当前场景。

## D15：第一步先选场景

状态：采用（T21，2026-09-24）

D14 允许"直接选场景"和"逐个子项确定场景"两种入口，但两种入口并存会让用户分不清自己在选什么。改为第一步只选场景，子项在选完场景后自动填好，并只能在场景内调整。逐项选择的规则仍保留在引擎底层，用于推导每个场景内哪些子项可选。

## D16：场景参数不在界面展示

状态：已被 D21 取代（T27，2026-09-28：轮次、本地训练、基座模型等作为维度 4、5 的子项展示，全部带推荐值）

基础模型、rank、轮次、PSI 算法等都有默认值，不是用户必须做的选择，展示出来只会增加负担。去掉原"维度 4 场景参数"，默认值只在 FrontendRunPlan 中记录。

## D17：数据接入 = 匹配已登记数据 + 上传后由 Agent 检查

状态：采用（T23，2026-09-24）

数据接入步骤先按前面的选择列出数据要求，并从已登记的联邦数据中匹配符合条件的数据供勾选；用户也可以上传自己的数据。上传后由 Agent 按数据契约检查格式、字段和条数，不符合时说明原因和修改建议；有未通过或检查中的上传时不能开始。检查规则是确定性的，Agent 负责解释，不能放过不符合的数据。

## D18：demo 只保留最通用的方法；安全按框架实际能力列出

状态：采用（T24，2026-09-24）

demo 阶段不追求全覆盖，场景、子项和策略只保留最通用、最主流的（Agent / 大模型相关例外）：删除"模型与 Adapter 聚合"场景、参与方形态子项（只做跨机构）、模型服务 Endpoint，以及 FedAdam / FedYogi、TIES、DARE、跨站点交叉验证等次常用策略。

安全维度不再是与方法无关的五档抽象预设。调研 Flower、NVFlare、FATE 后改为：基础保护和协议内置保护自动生效（例如 FATE 纵向协议自带 Paillier 和 ECDH PSI、NVFlare 联邦统计自带最小计数和加噪）；可选增强只列策略所在 runner 实际提供的（Flower 的 SecAgg+ 和差分隐私、NVFlare 安全 XGBoost 的 CKKS、机密 FedRAG 的 TEE），可以叠加，且不需要切换 runner。

## D19：场景按运行方式重分为 4 个；横向照 Flower，纵向用 NVFlare

状态：采用（T26，2026-09-25）；纵向框架部分已被 D22 取代

场景的根本差别在"各方怎么参与"：要么启动客户端节点、和平台保持连接、按轮协作（横向 / 纵向联邦训练）；要么上传一次文件、平台算完给结果（联邦统计分析、Agent 记忆联邦）。因此场景减为 4 个，并按这两种运行方式分组；数据接入随之分为"连接节点"和"上传文件"。

- LoRA 联邦微调与模型联合训练流程相同，只是每轮交换的对象不同，并入横向联邦训练，作为子项"共享方式"。
- 纵向单独成为场景：需要隐私求交、只有一方有标签、逐步交换加密中间结果、模型按参与方分片，和横向流程完全不同；纵向也没有"全量 / LoRA"之分。
- 删除联邦评估（评测在各方本地完成，平台只收分数；评测仍是每次运行的一个步骤）和联邦检索（在线问答服务，不是一次任务；"联邦训练检索模型"本质是横向联邦训练）。
- Agent / Skill 协作改为 Agent 记忆联邦：各方上传记忆文件，平台脱敏、去重、处理冲突、回放验证后生成新的记忆文件，参考 Agent KB、Collaborative Memory。
- 子项"协作目标、各方投入、数据关系"在场景确定后没有可选内容，删除。
- 框架：Flower 持续维护（2026-09-22 发布 1.38），Apache-2.0，可嵌入平台，横向照它的 SuperLink / SuperNode / ServerApp / ClientApp 方式做。FATE 最后发版是 2024-07-31，已停止更新，纵向改用 NVFlare（2026-09-04 发布 2.9.0）的安全纵向 XGBoost（ECDH PSI + Paillier）。纵向逻辑回归因此不再收录。

## D20：组队方式采用"发起 + 邀请"和"组织内部多节点"

状态：采用（T27，2026-09-28）

跨机构联邦最常见的是 2–5 家、一家发起。平台以项目为单位：发起方配置并创建项目，邀请合作机构；受邀机构依次接受、绑定节点、授权数据、确认方案。同一机构的多个节点（或多份文件）也可以各作为一方，单个机构就能完整使用平台。

- 配置只由发起方决定，其他方确认或拒绝（与隐语 SecretPad 的项目 → 合作节点 → 数据授权一致）；确认后修改配置必须新建项目。
- 平台默认不展示其他机构的任何内容；同一项目只看到彼此授权的描述信息。
- 资源目录（撮合）和开放招募暂不做，前者只在融资材料中说明。
- 演示环境预置示例机构，由模拟器自动完成加入流程。

## D21：配置改为云服务下单式的 7 个维度

状态：采用（T27，2026-09-28）

对比了"8 个流程步骤直接给用户选"和"只选场景 + 大白话问题"两种方案：前者太专业，后者不够专业、不适合融资展示。最终按云服务下单的顺序设计 7 个维度（协作场景 → 参与方与算力 → 数据 → 模型 → 算法与训练 → 安全与隐私 → 评测与交付），用业内通用名词加一句说明；选完场景即按推荐值得到完整配置，用户只改关心的部分；右侧订单摘要显示配置清单、平台推导和资源与耗时预估。

- 资源排在方法之前：各方有什么算力决定能选什么模型，以资源最弱的一方为准（节点必须不低于项目要求）。
- 所有子项都有值，已选选项再点一次不会取消，可选能力用"关闭"表示；子项分不适用、锁定、可选三种状态。
- 安全与隐私仍是一个维度，但子项按作用位置拆开（安全聚合、差分隐私、加密计算、输出保护），协议内置的显示为锁定。

## D22：纵向联邦改用隐语 SecretFlow；只收录现在主流在用的方法

状态：采用（T27，2026-09-28）

判断"主流"看现在的使用情况，而不只看是否发版。FATE 最后发版为 2024-07-31，新项目多转向隐语（例如联通 2024 年在 FATE、SPDZ、隐语之间选型后选了隐语），但 FATE 主打的 SecureBoost、纵向逻辑回归仍是纵向联邦的主流方法，因此方法保留、改由隐语执行：SecureBoost（HEU，Paillier / OU）、SS-LR（SPU 秘密分享），隐私求交用 PSI v2 的 ECDH / RR22。横向训练继续照 Flower 的方式（1.38，2026-09-22）；NVFlare 可作为 Flower 应用的生产运行环境，不作为用户选项。

即使方法在框架里是打包好的一整套协议，也按维度拆开：协议内固定的部分显示为锁定，能选的部分（求交协议、同态加密方案、树数量）开放出来。

## D23：API 优先，人和 Agent 用同一套接口；平台本身不需要 GPU

状态：采用（T28，2026-09-28，目标架构，尚未实现）；Agent 模型与沙箱部分已被 D24 取代

- 先定义 OpenAPI，Web 控制台、CLI（`fedctl`）、MCP Server 和 SDK 都由它派生；配置用与 7 个维度对应的声明式 `project.yaml`，先 `plan`（输出订单摘要）再 `apply`。
- Agent 只通过 MCP / CLI 调用平台，没有旁路；使用短期、最小权限令牌，在隔离的工作沙箱中执行。策略引擎先于 Agent：只读自动、可逆操作自动并审计，启动运行、交付、邀请外部机构、升级节点需人工审批；Agent 不接触原始数据。
- 平台内的 Agent 用自托管的 Claude Agent SDK，默认模型 Claude Opus 5，简单高频子任务用 Claude Haiku 4.5；不能调用外部 API 的客户可换私有化模型。
- 每次运行按需创建沙箱（k3s + gVisor 起步），只拉取签名镜像；参与方只装一个节点程序 `fs-node`，主动出站 mTLS 连接。
- 资源：控制面、编排、聚合、统计、记忆合并和 Agent 都不需要 GPU；GPU 只在训练发生的地方需要（正式运行在各参与方节点，由参与方自备；在单机上模拟多方的大模型 LoRA demo 需要 1 张 24 GB 显卡）。

## D24：Agent 使用我方大模型 API；沙箱统一为 K8s Agent Sandbox，gVisor 与 Firecracker 分工

状态：采用（T29，2026-09-28，目标架构，尚未实现）；沙箱隔离的分工已被 D25 取代

- Agent 不使用外部模型厂商，改用我方提供的大模型 API，经模型网关以 OpenAI 兼容接口调用；Agent 框架与模型解耦（默认 Pydantic AI，长流程用 LangGraph），只把平台 MCP / CLI 当作工具。模型需要稳定的工具调用和 JSON 结构化输出。候选模型服务为 OpenRouter 或 GLM（均为 OpenAI 兼容），面向国内机构优先 GLM。
- 平台共有六类沙箱：协调 / 聚合、统计 / 记忆合并、评测、上传检查、Agent 工作、镜像验证。统一用 Kubernetes Agent Sandbox（SandboxTemplate / SandboxClaim / SandboxWarmPool）管理。
- 默认隔离用 gVisor（不需要 KVM，可通过 nvproxy 用 GPU）；模型生成的代码和外部上传的文件用 Kata + Firecracker（虚拟机级隔离，Agent 沙箱最主流的隔离技术，但需要 KVM、暂不支持 GPU）。服务器不支持 KVM 时全部先用 gVisor。
- 托管的 Agent 沙箱服务（E2B、Daytona、Modal 等）不采用：平台需要私有化部署，且沙箱要访问平台内部服务。

## D25：沙箱 microVM 优先，gVisor 兜底

状态：采用（T30，2026-09-28，目标架构，尚未实现）

- 除评测沙箱外，协调 / 聚合、统计 / 记忆合并、上传检查、Agent 工作、镜像验证 5 类沙箱默认用 microVM（Kata Containers + Firecracker）：虚拟机级隔离，是当前 Agent 沙箱的主流做法，也没有 gVisor 在读写密集负载上的额外开销。
- gVisor 只用于需要 GPU 的评测（nvproxy 共用宿主机驱动；Firecracker 稳定版不支持 GPU 直通，整卡直通在单卡服务器上不实用），以及宿主机不支持 KVM 时的整体兜底。
- 部署时按节点是否有 `/dev/kvm` 选择 RuntimeClass；架构与代码不依赖具体服务器，服务器检查只影响部署配置。

## D26：平台内部 Agent = 自研薄层 + 通用库；Agent 只做理解、解释、起草和诊断

状态：采用（T31，2026-09-28，目标架构，尚未实现）

- 不自己写模型调用与工具循环，也不直接用通用 Agent 产品做平台内部 Agent。底层用 Pydantic AI（模型无关、原生 MCP、结构化输出，借 Temporal 集成做持久执行，与平台工作流共用），上层自研平台 Agent 层（角色、工具白名单、输出格式、权限与审批、上下文拼装、审计、回归测试）。不再单独引入 LangGraph。
- Codex SDK（编程 Agent，只支持 Responses 接口）暂不引入，以后需要写代码的子任务时再评估放入 microVM 工作沙箱；Hermes Agent（个人助手型、自我演化的技能与记忆）不做平台内部 Agent，定位为可通过 MCP 操作平台的外部 Agent，其记忆与技能可作为 Agent 记忆联邦的输入。
- 适合 Agent：配置助手、准入解释、数据问题说明、运行诊断、运维巡检、评测报告、记忆合并、平台问答。不用 Agent：准入与合规判定、联邦计算本身、训练中的实时决策、权限审批与交付决定、任何接触原始数据的环节、数据校验本身、常规调度、审计计费、安全事件的自动处置。Agent 的输出一律再经过确定性校验。

## D27：只做联邦 Agent；场景分横向、纵向、迁移，每个算法只属于一个场景

状态：采用（T32 方案，T33 按用户意见调整后落地，2026-09-28）

- 平台只做联邦 Agent：参与方共享文本形式的推理经验，不共享模型参数、题目和答案。原来包含 Flower、隐语等框架的 7 维度配置太大，全部去掉。
- 场景沿用联邦学习的三分法：横向、纵向、迁移。用户先选场景，再选算法，再选数据。
- 每个算法只属于一个场景。FoT 属于横向：T32 方案里的"FoT 源 → 目标"迁移用法已取消，迁移和纵向各自接自己的算法，目前待定，界面显示为规划中。
- 算法按插件登记（参与方步骤 + 服务端步骤 + 适用数据 + 参数 + 产出物 + 指标），对应上游的 `LocalReasoningClient` / `GlobalReasoningServer`，页面和调度不因新算法改动。
- 老平台 demo（TrustFLAIR）只作为以前设计的参考，不按它逐项对照设计。

## D28：参与方分平台托管和参与方本地两种运行位置

状态：采用（T33，2026-09-28；本地客户端尚未实现）

- 每份数据由一个参与方持有，一份数据就是一个参与方 Agent。
- **平台托管**：由平台运行这一方的 Agent，题库在平台，用于公开数据、演示和算法验证，第一版以它为主。
- **参与方本地**：参与方运行 `fedagent-client`，题库和模型密钥留在本地，每轮只上传 trace（上传前可审查），用于真实的跨机构联邦。
- 不再做"发起 + 邀请 + 节点交付"的组队流程；本地参与方连上客户端即可被选入任务。
- 界面上明确写出平台托管时平台能看到题库，避免把演示模式说成隐私保护。

## D29：先做前端原型，结果用确定性的示例数据并统一标注

状态：采用（T33，2026-09-28）

- 按用户要求，这一阶段不跑通后端，先把前端、整体架构和使用方式定清楚。
- 任务运行是加速的模拟。准确率、trace 数、洞见库和 token 由任务 id 确定性生成，刷新后不变；界面在结果、洞见库、上传记录和侧栏都标"示例数据"，试用页的回答标"示意"。
- 能在浏览器里真实做的就真实做：题库 JSONL 检查、导出洞见库 JSON、调用次数的精确计算。
- 接入后端时只替换数据来源（API + 检查点），页面、状态机和配置校验不变。

## D30：任务参数与已审计的复现器一一对应

状态：采用（T33，2026-09-28；引擎尚未实现）

- FoT 引擎由已审计的复现器拆分而来：上游 Prompt 1–5 原样使用，保留检查点续跑和哈希审计，保留复现器命令行和测试作为回归。
- 平台的轮次、试跑题数、模型、洞见库条数、trace 密度、每题 trace 上限、汇总重试、种子、并发都直接对应复现器参数。只有汇总重试上限的默认值不同：平台默认 5 次，超过后暂停任务，而复现器默认一直重试，可能让费用失控。
- 预估里调用次数精确计算；token、时长和费用按公开的口径估算，首次真实运行后校准。并发数与复现器一致，是所有参与方共用的线程池。

## D31：洞见库是任务的产出物，发布后可以试用、导出和调用

状态：采用（T33，2026-09-28；试用与 API 尚未接后端）

  - 数据用多选下拉：参与方是联邦任务的主体，下拉会把"选了哪几方"藏起来；分组表格既能看清也够紧凑；

## D38：第三轮检查：新增、编辑改为独立页面，确认和结果提示全站统一

状态：采用（T41，2026-09-29）；D35 里"延后"的几项仍然延后

- 根因多在共用部分，所以改共用部分：
  - **创建流程两种形态**：新建任务是独立页面，新增参与方、新增和编辑接口却是列表页顶部的开关。改为独立路由（`#/participants/new`、`#/models/new`、`#/models/:id/edit`），从新建任务过来带 `?from=new-task`，保存后回到新建任务并自动选上新数据集。

## D47：后端按通用插件体系设计：清单声明数据流，平台执行；FoT 是第一个插件

状态：采用（T51，2026-10-02）；取代 ARCHITECTURE 里原来的后端草案（插件接口只有"参与方一轮 + 服务端一轮"、API 按经验库命名、用 Docker Compose 部署）

- 用户要求：先改后端设计文档，整体后端要方便以后扩展各种算法、参与方和数据；之后先在本地实现和测试，没问题再部署到服务器。
- 原草案的问题：
  - 插件接口只能表达"各方本地一步 → 服务端汇总 → 下发"，纵向（角色、样本对齐、一轮多次交互）和迁移（源方 → 目标方）套不进去；
  - API、服务、客户端协议、运行目录都按 FoT 命名和设计（经验库、trace、`solve_r{n}.jsonl`）；
  - 部署写的是 Docker Compose，但实验室服务器没有 Docker 和 sudo。
- 做法：
  - **插件**：算法、任务类型、判分、执行器、数据格式、模型服务都是插件（Python entry points）；三种场景的规则写在核心里。
  - **算法清单**：声明角色、步骤（在哪一方执行、按样本还是按站点拆工作单元、读写哪些通道、是否生成产出、进度记什么）、交换通道、产出、评估和参数。前端注册表就是清单的前端版本，接入后端后从 API 读。
  - **数据流由平台执行**：每一步只拿到清单允许的能力。服务端读不到数据集，算法步骤默认读不到标注，没声明的通道发不出去；判分在持有标注的一方执行，只上报汇总。
  - **编排**：每一步拆成有编号的工作单元，写盘后才算完成；模型调用按工作单元记账，续跑不重复计费；每个运行中的任务一个子进程，由常驻的 runner 管理。
  - **执行器**：平台托管和本地客户端执行同一个插件包；以后加隔离环境、参与方自己的 Agent 服务。
  - **消息**：跨站点的内容都经平台转发并留档；每一步是一道栅栏。
  - **部署**：用户进程加部署脚本，uv、Python、代码和数据都放在 `~/fedagent-studio/` 里。
  - **测试**：SDK 自带契约测试，在小数据和假模型上检查数据流声明被遵守、杀掉后续跑结果一致。
- 没采用：
  - **Celery、RQ 一类任务队列**：要另起 Redis；它们适合短任务，长时间、有状态、要逐单元续跑和暂停的多轮流程仍要自己写。
  - **Temporal、Prefect 一类工作流引擎**：能做持久化的工作流，但要额外的服务和数据库，服务器又没有 Docker；现在一台机器、同时一个任务，用不上。以后多机时可以再评估，编排层的接口不变。
  - **Flower 一类联邦学习框架**：通信的单位是"一方的一整轮"，我们要按样本记检查点和账本，免得重复计费；大多数参与方是平台托管、只调模型接口，不需要单独的节点进程；暂停、续跑、记账仍要自己做。以后接入参数聚合类的联邦训练时，可以把它作为一种执行器接进来。
  - **参与方之间直连**：消息不经平台，就没法审计和追溯。
  - **每次运行起一个沙箱**：现在的算法不执行生成的代码，只调模型接口；以后只给执行代码的步骤或判分用隔离环境。

## D48：后端第一版的实现取舍：状态都在数据库，单个访问令牌，客户端安装包由平台提供

状态：采用（T52，2026-10-02）；在 D47 的设计内，记下实现时定的细节。其中"访问令牌"一项由 D49 改为可选、暂时关闭

- 用户要求：按 T51 的设计先在本地实现，测试没问题再部署到服务器；模型用 OpenAI 兼容的接口，之后自己在界面上配置。
- 做法：
  - **代码结构**：平台核心按职责分文件（`api.py`、`engine.py`、`runner.py`、`gateway.py`……），没有按 ARCHITECTURE 草案再分子包；第一版代码量不大，分包只会多一层引用。插件、SDK、客户端仍是独立的包，边界不变。
  - **运行状态都在数据库**：工作单元、各站点的状态、消息、上报值、调用账本都在 SQLite 里，一步的结果和它发出的消息、上报一起提交，要么都在、要么都不在，续跑只看数据库。运行目录只放冻结的配置、日志、产出版本和消息的副本。设计里的 `units/`、`calls.jsonl`、`metrics.json` 没有写成文件；FoT 按复现器格式写的插件文件留到逐文件核对时再做。
  - **访问令牌**：一个令牌，部署时生成，只保存在服务器的 `data/admin-token`；界面第一次打开时填，记在这个浏览器里。平台里存着模型密钥、能花钱，tailnet 里也可能有别的设备，所以即使只在内网也要令牌。账号和角色以后再加。
  - **runner 重启**：收到 SIGTERM 时先结束它起的任务进程，任务保持"运行中"，下一个 runner 从检查点继续；被强行结束时，新 runner 先结束遗留的任务进程（核对进程的命令行），再续跑。任务进程放在自己的会话里，终端的 Ctrl-C 不会越过 runner 直接打断它们。
  - **客户端安装包由平台提供**：部署时用 `uv build` 构建客户端、SDK 和插件的 wheel，api 在 `/client/` 下提供；界面上的命令用完整地址安装。
  - **模型**：只接 OpenAI 兼容的接口，由用户在"模型接口"里配置；所选接口没配好时后端校验不通过，不能创建任务。内置的测试用假模型由插件给出回答，跑通流程不花钱。
  - **前端读数据**：TanStack Query 轮询（有运行中的任务时 2 秒），没有用 SSE；只有新建任务的草稿留在浏览器里。
- 没采用：
  - **把客户端写成 `pip install fedagent-client`**：这几个包没有发布到公共仓库，装不上；以后有人注册同名的包，会装到别人的代码。
  - **自建包索引加 `--extra-index-url`**：pip 会同时看公共仓库，同名包版本更高时会装错（依赖混淆）。
  - **不设访问令牌**：理由见上。
  - **任务进程和 runner 在同一个进程组、一起收信号**：Ctrl-C 会直接打断正在写结果的任务进程；现在由 runner 统一结束，效果一样，顺序可控。

## D50：单元结果只由领取它的那次尝试保存；消息按固定顺序投递；接口检查按插件声明的生成参数

状态：采用（T54，2026-10-05）

- 起因：契约测试在并发负载下偶尔失败（暂停续跑和一次跑完的结果不一致），查出两处不确定：消息按写入顺序读出；保存单元结果"先查后写"，暂停后续跑时同一个单元可能写两次。另外接入胃袋AI 时，原来的"测试连接"只发一条 16 token 的请求，查不出模型是否接受任务真正用的参数。
- 做法：
  - **保存结果**：一条条件更新把单元从领取时的状态改为完成（平台执行的单元还要对上尝试次数），成功了才写消息、上报和产出；对不上就丢弃这次结果。这是常见的"围栏"做法，不依赖进程是否被及时结束。
  - **消息顺序**：按发送方在任务里的顺序、步骤、样本在数据集里的顺序、同一单元内的发送顺序。插件不用自己排序，也不会因为并发而得到不同的输入。
  - **接口检查**：插件声明最严格的生成参数（`model_settings`），平台按它逐个模型检查，并读接口的模型列表。
- 没采用：
  - **只在测试里等旧线程结束再续跑**：只能修测试，生产环境里本地客户端重复提交、进程没被及时结束时还会重复写入。
  - **插件自己给收到的消息排序**：每个插件都要记得做，容易漏；顺序是平台投递的事。
  - **遇到不支持的参数自动去掉再重试**（类似 LiteLLM 的 drop_params）：现在用到的模型都接受这些参数，暂时不需要；真遇到时先在检查结果里明确显示，再决定是否支持自动调整，避免悄悄偏离论文设置。

## D52：模型调用一律流式；失败尝试的调用作废，重试时重新调用

状态：采用（T56，2026-10-05）

- 起因：真实模型全流程测试里，中转偶尔返回空回答（200、0 token），账本把它当成功的调用，单元重试时又从账本取回，任务暂停后继续也跑不下去；中转在 Cloudflare 后面，超过约 120 秒没有响应就 524，FoT 的反思、归类和难题的试用都会碰到。
- 做法：
  - **流式**：所有请求用 `stream: true`，最后一块取 token 用量；不支持时自动改普通请求。这是经代理调用长生成的通行做法，也让以后在界面上显示生成进度成为可能。
  - **账本**：只有成功、且所在单元没有失败的调用能在续跑时取回。单元某次尝试失败时把这次的调用标为作废（费用照记），重试时重新调用。账本的用途是"中断后不重复计费"，不是"把失败的结果再用一次"。
  - **重试范围**：5xx 全部重试（501、505 除外）；空回答且不计 token 也重试。
- 没采用：
  - **调大客户端超时**：524 是 Cloudflare 在中转前面断开的，客户端超时再长也没用。
  - **插件在重试时改提示词绕开账本**：每个插件都要记得做，而且会改变提示词，偏离论文设置。
  - **账本不记空回答以外的失败结果**：步骤怎样算失败只有插件知道（格式不对、找不到答案），平台按"单元失败"统一处理更可靠。

## D53：本地工作单元按领取次数校验，执行中独立续租

状态：采用（T58，2026-10-05）

- 领取返回 `attempt`，输入、续租、完成、失败均校验 token 持有者、次数、未过期租约和任务状态。重领后拒绝旧结果，同一次完成响应丢失可安全重发。
- 客户端 0.1.1 一次领取一个单元，后台线程在慢模型调用和人工审查期间续租，避免旧版批量领取后串行等待导致租约过期。
- 平台托管和本地客户端都只向插件提供任务冻结的样本集合；试跑标注分母在第一轮评估结束后使用实际汇总。
- 这是客户端协议变更，旧客户端需要升级，不允许无请求头的兼容提交绕过次数校验。
