# 关键设计决策

## D1：以工作负载为第一选择

状态：由 D8–D10 细化（2026-09-24）。入口仍是"想完成什么"，但改为"协作目标"维度，工作负载变为维度 1–5 落到的场景模板。

用户通常先知道“想完成什么”，而不是先知道 FedAvg、MPC 或某个框架名。因此入口是工作负载，算法和运行时在下一层出现。

## D2：数据关系与参与拓扑分开

状态：采用

横向/纵向描述数据分布，Cross-silo/Cross-device 描述组织和设备形态。两者影响不同的算法、协议、资源和治理要求，不能合并成“数据类型”。

## D3：用保护目标替代单一“加密方式”

状态：采用

SecAgg、DP、HE、MPC 和 TEE 解决的问题不同，也可能组合使用。用户先选隐藏单方更新、样本级隐私、加密计算等目标，平台再映射机制，并在后端验证 runner 是否真的支持。

## D4：运行时和输出由平台解析

状态：采用

Flower、FATE 或自定义 worker 不应成为与业务目标平级的自由选项。平台根据工作负载、策略、拓扑和保护要求选择兼容 runner；评测和输出同理。

## D5：统一控制面，不统一算法语义

状态：采用

所有任务共享 Run 生命周期和基础设施契约，但模型训练、PSI、联邦统计、FedRAG 和 Skill merge 使用不同 runner adapter。通用性体现在可插拔契约，而不是一个巨大执行器。

## D6：硬规则优先于 Agent

状态：采用

格式、schema、模型架构、隐私预算和权限等确定性条件由 policy engine 决定。Agent 负责解释、建议和长尾分析，不能绕过拒绝结果，也不能直接执行上传内容。

## D7：先打通一条纵向切片

状态：调整（2026-09-24）。先用前端确认维度分层，再选两个结构差异大的场景做后端 demo；LoRA 仍是候选之一。

前端可以展示完整平台边界，但后端第一阶段只实现 PEFT / LoRA。完成上传、准入、沙箱、执行、评测和发布后，再接第二类工作负载验证抽象。


## D8：维度按"用户最先能回答的问题"排序，只有前层约束后层

状态：采用（T14，2026-09-24）

顺序为协作目标 → 各方投入 → 数据关系 → 参与方形态 → 模型形态 → 协作策略 → 安全与信任 → 场景参数。算法和保护依赖前面所有信息，所以放在最后。单向约束保证后面的选择不会让前面失效。

## D9：新增"各方投入"维度

状态：采用（T14）

"多轮联邦训练"和"已训练产物聚合"的差别在于各方拿出来的是什么，而不是两个平台。用这个维度统一两者，并由它决定输入接入方式和执行模式。

## D10：新增"模型形态"维度，场景模板变为路径落点

状态：采用（T14）

模型类别放在策略之前约束策略，解决"树模型 + FedAvg"这类非法组合；LoRA 等成为同一层下的共享方式（个性化、异构已在 D13 中删除）。9 类工作负载改为 10 个场景模板（PEFT 拆成联邦微调与已训练产物聚合），作为维度 1–5 的落点，同时保留模板快捷入口。

## D11：保护可用性由计算类型和 runner 能力判断

状态：采用（T14）

每条策略声明计算类型（可加、比较、拼接组合、纵向协议、需理解内容），保护预设据此判断能否使用，并给出原因。不用"某场景不能用某保护"的黑名单。完整性（鲁棒聚合）曾作为可选叠加，已在 D13 中删除。

## D12：前端统一 FrontendRunPlan，按执行模式模拟

状态：采用（T15）

删除旧 LoRA mock，所有场景共用一个状态机，由模拟器按执行模式生成阶段内容，并显示真实耗时预估。FrontendRunPlan 是后端 RunSpec 的前身。

## D2 补充：本地模拟不属于参与方形态

2026-09-24：本地模拟是运行环境，移到执行预设；"无训练数据协作"不再是数据关系取值，改为数据关系不适用时隐藏该维度。

## D13：只收录主流方法，大模型 / Agent 相关方法保留并标"前沿"

状态：采用（T17，2026-09-24）

平台的分层用来帮用户选到实际可用的方法，而不是做学术综述。只保留有成熟开源实现、实际用得多的方法；小众方法即使在论文和 benchmark 里很成熟也不收录；大模型 / Agent 相关的方法还在快速演进，但方向重要，保留并标"前沿"。"成熟 / 试点 / 研究"三档标签取消，主流方法不打标签。删除清单见 DIMENSIONS.md 的"未收录"。

## D14：场景作为维度 1，定位场景的问题作为它的子项

状态：采用（T20，2026-09-24）

原来的维度 1–5 实际上都是在定位场景，场景是它们的落点。把场景提升为维度 1、原维度 1–5 改为子项 1.1–1.6，能直接表达"先确定场景，再在场景内选方法"。已选选项再点一次即取消；场景确定后子项必须保留一个选择，不能取消，想换场景就直接点另一个场景或取消当前场景。

## D15：第一步先选场景

状态：采用（T21，2026-09-24）

D14 允许"直接选场景"和"逐个子项确定场景"两种入口，但两种入口并存会让用户分不清自己在选什么。改为第一步只选场景，子项在选完场景后自动填好，并只能在场景内调整。逐项选择的规则仍保留在引擎底层，用于推导每个场景内哪些子项可选。

## D16：场景参数不在界面展示

状态：已被 D21 取代（T27，2026-09-28：轮次、本地训练、基座模型等作为维度 4、5 的子项展示，全部带推荐值）

基础模型、rank、轮次、PSI 算法等都有默认值，不是用户必须做的选择，展示出来只会增加负担。去掉原"维度 4 场景参数"，默认值只在 FrontendRunPlan 中记录。

## D17：数据接入 = 匹配已登记数据 + 上传后由 Agent 检查

状态：采用（T23，2026-09-24）

数据接入步骤先按前面的选择列出数据要求，并从已登记的联邦数据中匹配符合条件的数据供勾选；用户也可以上传自己的数据。上传后由 Agent 按数据契约检查格式、字段和条数，不符合时说明原因和修改建议；有未通过或检查中的上传时不能开始。检查规则是确定性的，Agent 负责解释，不能放过不符合的数据。

## D18：demo 只保留最通用的方法；安全按框架实际能力列出

状态：采用（T24，2026-09-24）

demo 阶段不追求全覆盖，场景、子项和策略只保留最通用、最主流的（Agent / 大模型相关例外）：删除"模型与 Adapter 聚合"场景、参与方形态子项（只做跨机构）、模型服务 Endpoint，以及 FedAdam / FedYogi、TIES、DARE、跨站点交叉验证等次常用策略。

安全维度不再是与方法无关的五档抽象预设。调研 Flower、NVFlare、FATE 后改为：基础保护和协议内置保护自动生效（例如 FATE 纵向协议自带 Paillier 和 ECDH PSI、NVFlare 联邦统计自带最小计数和加噪）；可选增强只列策略所在 runner 实际提供的（Flower 的 SecAgg+ 和差分隐私、NVFlare 安全 XGBoost 的 CKKS、机密 FedRAG 的 TEE），可以叠加，且不需要切换 runner。

## D19：场景按运行方式重分为 4 个；横向照 Flower，纵向用 NVFlare

状态：采用（T26，2026-09-25）；纵向框架部分已被 D22 取代

场景的根本差别在"各方怎么参与"：要么启动客户端节点、和平台保持连接、按轮协作（横向 / 纵向联邦训练）；要么上传一次文件、平台算完给结果（联邦统计分析、Agent 记忆联邦）。因此场景减为 4 个，并按这两种运行方式分组；数据接入随之分为"连接节点"和"上传文件"。

- LoRA 联邦微调与模型联合训练流程相同，只是每轮交换的对象不同，并入横向联邦训练，作为子项"共享方式"。
- 纵向单独成为场景：需要隐私求交、只有一方有标签、逐步交换加密中间结果、模型按参与方分片，和横向流程完全不同；纵向也没有"全量 / LoRA"之分。
- 删除联邦评估（评测在各方本地完成，平台只收分数；评测仍是每次运行的一个步骤）和联邦检索（在线问答服务，不是一次任务；"联邦训练检索模型"本质是横向联邦训练）。
- Agent / Skill 协作改为 Agent 记忆联邦：各方上传记忆文件，平台脱敏、去重、处理冲突、回放验证后生成新的记忆文件，参考 Agent KB、Collaborative Memory。
- 子项"协作目标、各方投入、数据关系"在场景确定后没有可选内容，删除。
- 框架：Flower 持续维护（2026-09-22 发布 1.38），Apache-2.0，可嵌入平台，横向照它的 SuperLink / SuperNode / ServerApp / ClientApp 方式做。FATE 最后发版是 2024-07-31，已停止更新，纵向改用 NVFlare（2026-09-04 发布 2.9.0）的安全纵向 XGBoost（ECDH PSI + Paillier）。纵向逻辑回归因此不再收录。

## D20：组队方式采用"发起 + 邀请"和"组织内部多节点"

状态：采用（T27，2026-09-28）

跨机构联邦最常见的是 2–5 家、一家发起。平台以项目为单位：发起方配置并创建项目，邀请合作机构；受邀机构依次接受、绑定节点、授权数据、确认方案。同一机构的多个节点（或多份文件）也可以各作为一方，单个机构就能完整使用平台。

- 配置只由发起方决定，其他方确认或拒绝（与隐语 SecretPad 的项目 → 合作节点 → 数据授权一致）；确认后修改配置必须新建项目。
- 平台默认不展示其他机构的任何内容；同一项目只看到彼此授权的描述信息。
- 资源目录（撮合）和开放招募暂不做，前者只在融资材料中说明。
- 演示环境预置示例机构，由模拟器自动完成加入流程。

## D21：配置改为云服务下单式的 7 个维度

状态：采用（T27，2026-09-28）

对比了"8 个流程步骤直接给用户选"和"只选场景 + 大白话问题"两种方案：前者太专业，后者不够专业、不适合融资展示。最终按云服务下单的顺序设计 7 个维度（协作场景 → 参与方与算力 → 数据 → 模型 → 算法与训练 → 安全与隐私 → 评测与交付），用业内通用名词加一句说明；选完场景即按推荐值得到完整配置，用户只改关心的部分；右侧订单摘要显示配置清单、平台推导和资源与耗时预估。

- 资源排在方法之前：各方有什么算力决定能选什么模型，以资源最弱的一方为准（节点必须不低于项目要求）。
- 所有子项都有值，已选选项再点一次不会取消，可选能力用"关闭"表示；子项分不适用、锁定、可选三种状态。
- 安全与隐私仍是一个维度，但子项按作用位置拆开（安全聚合、差分隐私、加密计算、输出保护），协议内置的显示为锁定。

## D22：纵向联邦改用隐语 SecretFlow；只收录现在主流在用的方法

状态：采用（T27，2026-09-28）

判断"主流"看现在的使用情况，而不只看是否发版。FATE 最后发版为 2024-07-31，新项目多转向隐语（例如联通 2024 年在 FATE、SPDZ、隐语之间选型后选了隐语），但 FATE 主打的 SecureBoost、纵向逻辑回归仍是纵向联邦的主流方法，因此方法保留、改由隐语执行：SecureBoost（HEU，Paillier / OU）、SS-LR（SPU 秘密分享），隐私求交用 PSI v2 的 ECDH / RR22。横向训练继续照 Flower 的方式（1.38，2026-09-22）；NVFlare 可作为 Flower 应用的生产运行环境，不作为用户选项。

即使方法在框架里是打包好的一整套协议，也按维度拆开：协议内固定的部分显示为锁定，能选的部分（求交协议、同态加密方案、树数量）开放出来。

## D23：API 优先，人和 Agent 用同一套接口；平台本身不需要 GPU

状态：采用（T28，2026-09-28，目标架构，尚未实现）；Agent 模型与沙箱部分已被 D24 取代

- 先定义 OpenAPI，Web 控制台、CLI（`fedctl`）、MCP Server 和 SDK 都由它派生；配置用与 7 个维度对应的声明式 `project.yaml`，先 `plan`（输出订单摘要）再 `apply`。
- Agent 只通过 MCP / CLI 调用平台，没有旁路；使用短期、最小权限令牌，在隔离的工作沙箱中执行。策略引擎先于 Agent：只读自动、可逆操作自动并审计，启动运行、交付、邀请外部机构、升级节点需人工审批；Agent 不接触原始数据。
- 平台内的 Agent 用自托管的 Claude Agent SDK，默认模型 Claude Opus 5，简单高频子任务用 Claude Haiku 4.5；不能调用外部 API 的客户可换私有化模型。
- 每次运行按需创建沙箱（k3s + gVisor 起步），只拉取签名镜像；参与方只装一个节点程序 `fs-node`，主动出站 mTLS 连接。
- 资源：控制面、编排、聚合、统计、记忆合并和 Agent 都不需要 GPU；GPU 只在训练发生的地方需要（正式运行在各参与方节点，由参与方自备；在单机上模拟多方的大模型 LoRA demo 需要 1 张 24 GB 显卡）。

## D24：Agent 使用我方大模型 API；沙箱统一为 K8s Agent Sandbox，gVisor 与 Firecracker 分工

状态：采用（T29，2026-09-28，目标架构，尚未实现）

- Agent 不使用外部模型厂商，改用我方提供的大模型 API，经模型网关以 OpenAI 兼容接口调用；Agent 框架与模型解耦（默认 Pydantic AI，长流程用 LangGraph），只把平台 MCP / CLI 当作工具。模型需要稳定的工具调用和 JSON 结构化输出。候选模型服务为 OpenRouter 或 GLM（均为 OpenAI 兼容），面向国内机构优先 GLM。
- 平台共有六类沙箱：协调 / 聚合、统计 / 记忆合并、评测、上传检查、Agent 工作、镜像验证。统一用 Kubernetes Agent Sandbox（SandboxTemplate / SandboxClaim / SandboxWarmPool）管理。
- 默认隔离用 gVisor（不需要 KVM，可通过 nvproxy 用 GPU）；模型生成的代码和外部上传的文件用 Kata + Firecracker（虚拟机级隔离，Agent 沙箱最主流的隔离技术，但需要 KVM、暂不支持 GPU）。服务器不支持 KVM 时全部先用 gVisor。
- 托管的 Agent 沙箱服务（E2B、Daytona、Modal 等）不采用：平台需要私有化部署，且沙箱要访问平台内部服务。
